## 0. 요약

화면과 데이터 모델의 골격은 4개 스펙(A/B/C/D)을 대부분 따라가고 있고, PPT 런 분할 엔진·KST D-day·토큰 4종 분리 같은 어려운 부분은 제대로 되어 있다. 그러나 **"동작하는 것처럼 보이지만 실제로는 깨져 있거나 스펙의 핵심 요구를 빼먹은 부분"이 많다.**

- 인플루언서 지원폼 등 공개 페이지가 **다른 용도의 토큰 4개를 전부 HTML에 노출** (실측). 지원자가 페이지 소스만 보면 전체 지원자의 연락처·주소 페이지에 들어갈 수 있다.

- 이전 검수 문서 `docs/FIX-INSTRUCTIONS.md`의 9건이 **한 건도 반영되지 않았다.**
- `docs/VERIFICATION-REPORT.md`의 "100% 충족", "28/28 E2E 통과", "npm test" 주장은 재현할 수 없다. 유닛 테스트는 0개이고 `test` 스크립트도 없다.
- **DB는 SQLite가 아니라 JSON 파일 하나**다. 프로덕션 모드에서는 OS 임시 폴더에 저장되어 데이터가 사라질 수 있다.

## 1. 전제 확인: DB는 SQLite가 아니다

`lib/db/index.ts`를 보면 SQLite 관련 코드가 전혀 없다. `.data/db.json` 파일 하나를 모든 요청마다 `fs.readFileSync`로 통째로 읽고 `JSON.parse`한 뒤, 쓸 때는 통째로 `writeFileSync`한다.

| 항목 | 현재 상태 | 위험 |
|---|---|---|
| 저장 위치 | `process.env.VERCEL` 또는 `NODE_ENV=production`이면 `os.tmpdir()/marketing_db.json` | Vercel에서는 인스턴스가 바뀔 때마다 초기 샘플 데이터로 리셋. 일반 서버에서도 `next start`로 띄우면 프로젝트 폴더가 아닌 OS 임시 폴더에 저장됨 |
| 동시성 | 잠금 없음. read → 수정 → write | 두 요청이 겹치면 먼저 쓴 쪽 변경이 사라짐 (지원자 제출이 동시에 들어오면 한 명이 유실될 수 있음) |
| 성능 | PPT 템플릿을 base64로 같은 JSON에 저장. 오버뷰 페이지는 요청당 6번 파일을 읽고 파싱 | 템플릿 몇 MB 올리면 모든 페이지가 느려짐 |
| 기본 템플릿 | 최초 부팅 시 `generateDefaultPptBuffer()` 결과를 JSON에 박제 | 이후 코드에서 템플릿을 바꿔도 반영 안 됨. 실제로 현재 `.data/db.json`의 기본 템플릿은 2슬라이드짜리 구버전이고 코드는 3슬라이드다 |

**판단**: MVP 데모용으로는 쓸 수 있으나 외부(광고주·인플루언서)에게 링크를 배포하는 순간 데이터 유실 위험이 있다. 진짜 SQLite로 갈 거면 `better-sqlite3` 하나로 `lib/db/index.ts`의 함수 시그니처를 유지한 채 교체 가능하다. 그 전까지 최소한 `getDbFilePath()`의 `NODE_ENV === "production"` 분기는 제거하고, 쓰기를 직렬화하는 큐(또는 `proper-lockfile`)를 넣어야 한다.

## 3. 스펙 대비 미구현 / 불일치 (High)

### A. 인플루언서 시딩

1. **지원자 공유 페이지가 조회 전용이다.** 스펙 A-3, "인증 및 권한" 절은 `/applicants/[token]`에서 광고주가 최종선정/예비선정을 클릭할 수 있어야 하고, 이것이 "쓰기를 허용하는 유일한 공개 라우트"라고 못 박았다. `ApplicantTable`에 `isPublicShare` prop이 있지만 사용되지 않고, 공개 페이지는 별도 read-only 테이블이다.
2. **`changedBy`를 클라이언트가 보낸다.** `changeApplicantStatusAction`이 `changedBy: "agency" | "company"`를 파라미터로 받는다. `HANDOVER-B-C-D.md`가 정확히 이 패턴(`setStatus(actor, ...)`)을 금지했다. 현재는 항상 `"agency"`만 기록되고, `status_changed_at`(스펙 필수)은 타입에도 없다.
3. **선정 취소 시 관리시트 데이터가 삭제된다.** `updateApplicantStatus()`가 `selected`가 아닌 상태로 바뀌면 `seeding_records`를 splice한다. 진행단계·업로드 링크·조회수가 사라진다. 스펙은 "삭제하지 않음"이다. `rejected` 상태는 없고 `dropped`는 타입에만 있다.
4. **관리시트에 D-day가 없다.** 스펙 A-4의 핵심("업로드 기한 입력 시 D-day 자동 계산")인데 `SeedingSheetTable.tsx`는 `lib/seeding/dday.ts`를 import조차 하지 않는다. 캠페인 유형별 단계 분기도 없다(7개 단계가 항상 다 보임, `lib/seeding/stages.ts`는 아무 데서도 안 씀). 메모(`notes`) 편집 UI도 없다.
5. **중복 감지가 반쪽이다.** 서버에서 `findDuplicates()`(정규화 포함)를 계산해 넘기지만 `ApplicantTable`은 그 prop을 무시하고 원문 문자열로 다시 계산한다. 게다가 `duplicatesObj[a.contact] || duplicatesObj[a.sns_link]` 때문에 연락처가 다르면 SNS 중복은 절대 잡히지 않는다.
6. **CSV**: `reserved`(예비선정)가 "지원완료"로 나간다. 커스텀 문항 답변은 내보내지 않는다.
7. **신청폼 서버 검증 없음**: `submitApplicantAction`이 필수값·개인정보 동의·`is_published`를 검사하지 않는다. 모집 마감 후에도 액션을 직접 호출하면 접수된다. 커스텀 문항 `type`(number/select/checkbox)은 전부 text input으로 렌더링되고 select 옵션 편집 UI가 없다.
8. **캠페인 상태 전이 없음**: `status`는 영원히 `recruiting`이고 목록에는 영문 그대로 노출된다. 캠페인 수정/삭제 UI도 없다.
9. `used_ai_assist`는 항상 `true`로 저장된다.

### B. 인플루언서 행사

1. 행사 상태 변경·수정·삭제 UI 없음 (`deleteEvent`는 DB 함수만 존재).
2. **`event_at` 형식이 섞여 있다.** 모달의 `datetime-local` 값(`"2026-09-15T18:00"`, 타임존 없음)을 그대로 저장하고, 샘플은 ISO `Z`다. 화면은 `new Date(...).toLocaleString()`을 서버에서 호출하므로 Vercel(UTC)에서는 9시간 밀려 보인다. 오버뷰는 `event_at.split("T")[0]`로 UTC 날짜를 쓰므로 KST 새벽 행사는 전날 칸에 찍힌다. 스펙 D가 KST 고정을 요구한 이유가 그대로 재현된다.
3. 초대자 가져오기 후 `window.location.reload()`로 전체 새로고침.
4. 운영안 필드 중 `행사개요`·`프로그램`만 textarea로 하드코딩되어 사용자가 올린 템플릿의 긴 필드는 한 줄 input이 된다.

### C. SNS 운영

1. **콘텐츠 수정/삭제 UI가 없다.** 생성 후 캡션·해시태그·예정일·담당자를 고칠 수 없다. 광고주가 "수정요청"을 보내도 에이전시가 캡션을 고쳐 다시 승인대기로 올릴 방법이 없어서 워크플로우가 여기서 끊긴다.
2. `app/(dashboard)/sns/actions.ts:39`의 `submitSnsIntakeAction`은 토큰 검증 없이 `accountId`만 받는다. 공개 폼은 `app/sns-intake/actions.ts`의 검증 버전을 쓰지만, 검증 없는 쪽도 `"use server"` export라 외부에서 호출 가능하다. 삭제할 것.
3. 상태 select가 어떤 전이든 허용하고 서버 검증이 없다(스펙: "정해진 값 외 전이를 서버 액션에서 재검증").
4. 사전설문 응답 탭이 질문 문구 대신 "항목 1, 2, 3"으로 표시된다. 템플릿의 `questions`를 넘겨 매핑하면 된다.
5. 계정 상태(`active`→`ended`) 변경, 계정 수정/삭제 UI 없음.
6. 콘텐츠 캘린더가 클라이언트 `new Date()`로 월을 정한다(스펙: KST 서버 계산).
7. 월별 성과 집계 없음 (FIX #6).

### D. 오버뷰

1. **조회 실패를 빈 배열로 위장한다.** `page.tsx`가 `Promise.allSettled` 결과를 `status === "fulfilled" ? value : []`로 삼킨다. 스펙 D "에러 처리" 절이 예시 코드까지 들어 금지한 방식이고, "일부 데이터를 불러오지 못했습니다" 배너도 없다. (현재는 6개 조회가 전부 같은 JSON 파일이라 격리 자체가 의미 없기도 하다.)

3. 월 이동이 `<Link>`가 아니라 클라이언트 `router.push`. 오늘 날짜 강조 없음. 부모 행사가 없는 체크리스트 항목은 제외 대신 `href="#"`로 남는다.

## 4. 설계 외 코드 품질 문제 (Medium)

1. **`Partial<전체 타입>`을 그대로 `Object.assign`**: `updateSnsContentAction`, `updateEventAction`, `updateChecklistItemAction`, `updateInviteeRsvpAction`(이건 좁혀져 있음), `updateSeedingRecord`. 클라이언트가 `id`, `account_id`, `campaign_id`, `created_at`까지 덮어쓸 수 있다. 허용 필드를 화이트리스트로 좁힐 것.
2. **PPT 값 안의 줄바꿈** (실측): 출력 pptx의 `<a:t>` 안에 raw `\n`이 들어간다. PowerPoint는 `<a:t>` 안의 LF를 줄바꿈으로 보장하지 않는다(정식은 `<a:br/>`). `프로그램`·`월별계획`처럼 여러 줄 입력을 유도하는 필드가 한 줄로 뭉개질 가능성이 크니 실제 PowerPoint에서 열어 확인하고, `fillTemplate`에서 `\n`을 `</a:t></a:r><a:br/><a:r><a:t>` 형태로 변환하도록 고칠 것. 런 분할 병합 자체는 정상 동작한다(실측: 잔여 `{{` 0개).
3. **`jszip`이 devDependencies**인데 런타임(`lib/ppt/engine.ts`)에서 쓴다. 스펙 B가 명시적으로 옮기라고 했다. `npm ci --omit=dev` 환경에서 PPT 기능이 죽는다.
4. **테스트가 없다.** 유닛 테스트 0개, `package.json`에 `test` 스크립트 없음. `tests/e2e.test.js`는 Playwright를 직접 호출하는 스크립트로, 서버가 떠 있어야 하고 실패해도 exit 0이며 조건이 느슨하다(예: `page.$` 결과가 null이면 검사를 통째로 건너뜀). 스펙 B가 "반드시 테스트로 고정할 것"이라 한 PPT 런 분할 테스트도 없다.
5. **테마 구현 방식**: 스펙의 디자인 토큰(`bg-bg`, `bg-surface`, `text-textMuted` …) 대신 모든 파일이 hex 하드코딩(`bg-[#131418]`)이고, 라이트 모드는 `globals.css`에서 그 클래스명들을 `!important`로 덮어쓰는 방식이다. 지금은 동작하지만 새 화면에서 다른 hex를 쓰는 순간 깨진다. `prefers-color-scheme` 미지원, `@theme`의 `--font-geist-*` 변수는 정의된 곳이 없다.
6. **저장소 정리**: `app/(dashboard)/design-preview/`(테마 시안 페이지, 프로덕션에 노출), `data/db.json`(8/31자 구버전, git 추적 중), `docs/sql/*.sql`(Supabase용, 현재 구조와 무관), `.agents/`(3.7MB 스킬 파일). ESLint 설정 파일 없이 `lint` 스크립트만 있다.
7. `TokenShareBox`, `SnsAccountDetailClient`가 `window.location.origin`을 렌더 중에 읽어 SSR(localhost)과 클라이언트 값이 달라진다. 하이드레이션 경고 원인.
8. 설정 화면 `handleRemove` 등에서 `updated[idx].label = ...`처럼 state 배열 요소를 직접 변이한다. 동작은 하지만 React 규칙 위반.

## 5. 잘 된 부분

- PPT 엔진의 `<a:p>` 단위 런 병합과 XML 이스케이프는 스펙대로 구현되어 있고 실측으로도 잔여 플레이스홀더가 없다.
- `lib/seeding/dday.ts`의 KST 계산은 정확하다(서버 타임존과 무관).
- 캠페인당 토큰 4종·SNS 계정당 2종 분리 발급, 초대자 스냅샷 복사, 중복 초대 방지, 삭제 시 하위 데이터 정리, 낙관적 UI는 스펙 의도에 맞다.
- `tsc --noEmit` 통과. 라우팅 구조와 URL은 스펙과 일치한다.
