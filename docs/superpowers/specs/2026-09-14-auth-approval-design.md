# 아이디·비밀번호 로그인과 관리자 승인제 설계

작성: 2026-09-14

## 목적

지금 대시보드는 주소만 알면 누구나 열 수 있다. 로그인을 붙이고, **관리자가 승인한 계정만**
쓸 수 있게 한다. 로그인은 이메일이 아니라 **아이디와 비밀번호**로 한다.

## 범위

**포함**
- 아이디·비밀번호 가입과 로그인, 로그아웃
- 로그인 유지(체크박스로 선택)
- 승인 대기 / 활성 / 차단 상태
- 관리자용 사용자 관리 화면: 승인, 거절, 차단·해제, 비밀번호 초기화, 관리자 권한 부여·회수, 계정 삭제
- 첫 관리자를 만드는 스크립트
- **인증 관련 동작의 감사 로그** (승인·차단·권한 변경·삭제). 나머지 감사 로그 확대는 다음 작업.

**제외**
- 비밀번호 찾기(본인). 이메일이 없어서 본인이 스스로 찾을 길이 없다. 관리자가 초기화해 준다.
- 소셜 로그인, 2단계 인증
- 공개 페이지(지원폼·사전조사·공유·승인·사전설문)의 인증. 지금처럼 토큰으로 연다.

## 인증 방식

**Supabase Auth + 내부용 이메일.** 아이디 `kimmanager` 로 가입하면 Supabase 에는
`kimmanager@moa.local` 로 저장한다. 사용자는 이 주소를 보지도 입력하지도 않는다.

직접 구현하지 않는 이유: 비밀번호 해싱, 세션 갱신, 쿠키 보안은 틀리면 피해가 크고,
Next.js 문서도 직접 만들지 말라고 명시한다. 검증된 라이브러리에 맡긴다.

**아이디 규칙**: 영문 소문자, 숫자, 밑줄. 3~30자. 첫 글자는 영문. 중복 불가(Supabase 의
이메일 unique 제약이 보장).

**비밀번호 규칙**: 8자 이상. Supabase 기본 정책을 따른다.

**사전 준비(사용자 작업)**
1. Supabase 대시보드 → Authentication → Providers → Email → **Confirm email 끄기**.
   실제 메일함이 없는 주소라 확인 메일이 가면 가입이 완료되지 않는다.
2. `.env.local` 과 Vercel 에 `SUPABASE_ANON_KEY` 추가. 브라우저 쪽 세션 처리에 필요하다.

## 데이터

`profiles` 테이블을 새로 만든다. `auth.users` 와 1:1 이다.

| 컬럼 | 설명 |
|---|---|
| `id` | uuid PK, `auth.users(id)` 참조, on delete cascade |
| `username` | text unique. 아이디 원본(내부 이메일의 앞부분) |
| `display_name` | text. 화면에 보일 이름 |
| `role` | `admin` \| `staff` |
| `status` | `pending` \| `active` \| `blocked` |
| `created_at`, `approved_at`, `approved_by` | 승인 이력 |

가입하면 트리거가 `pending` / `staff` 로 행을 만든다. 앱 코드가 만들지 않는 이유는,
가입 직후 프로필이 없는 순간이 생기면 안 되기 때문이다.

`audit_logs.entity_type` 체크 제약에 `user` 를 추가한다. 지금 값으로는 인증 동작을 기록할 수 없다.

## 클라이언트 두 개

| 파일 | 키 | 용도 |
|---|---|---|
| `lib/supabase/admin.ts` (기존) | service_role | 모든 데이터 읽기·쓰기. 변경 없음 |
| `lib/supabase/auth.ts` (신규) | anon + 쿠키 | 로그인·로그아웃·세션 읽기 |

`@supabase/ssr` 로 쿠키를 다룬다. 서버 컴포넌트용과 프록시용 생성 함수를 각각 둔다.

사용자 관리(승인·삭제·비밀번호 초기화)는 `auth.admin.*` 를 써야 하므로 service_role 클라이언트로 한다.

## 접근 통제 두 겹

Next.js 16 문서 권고를 따른다. 이 버전은 `middleware.ts` 가 아니라 **`proxy.ts`** 다.

**1단계 — `proxy.ts` (느슨한 검사)**
쿠키에 세션이 있는지만 본다. 없으면 `/login` 으로 보낸다. **DB 를 보지 않는다.**
모든 요청마다 도는 자리라 느려지면 안 된다.

matcher 에서 제외할 것: `/login`, `/signup`, 공개 토큰 경로 6종, `/api/media`, `/api/cron`,
정적 파일.

**2단계 — 데이터에 닿는 곳 (진짜 검사)**
`lib/auth/session.ts` 가 담당한다.

- `getCurrentUser()`: 세션 → `profiles` 조회. 없거나 비활성이면 null.
- `requireUser()`: 활성 사용자만 통과. `pending` 이면 `/pending`, `blocked` 면 `/blocked` 로 보낸다.
- `requireAdmin()`: 관리자만 통과.

적용 지점:
- `app/(dashboard)/layout.tsx` 에서 `requireUser()` — 대시보드 화면 전체를 덮는다.
- **모든 대시보드 서버 액션** — 화면을 거치지 않고 직접 호출될 수 있어 여기가 진짜 경계다.

### 서버 액션을 감싸는 방법

대시보드 서버 액션 55개가 전부 `lib/actions/result.ts` 의 `runAction()` 을 거친다.
공개 라우트 액션도 같은 함수를 쓰므로 `runAction` 안에 검사를 넣을 수는 없다.

같은 파일에 `runAuthedAction()` 을 새로 만들고, 대시보드 액션 11개 파일이 그것으로 바꾼다.

```ts
export async function runAuthedAction<T>(
  fn: (user: SessionUser) => Promise<T>
): Promise<ActionResult<T>>
```

콜백이 현재 사용자를 받는다. 다음 단계의 감사 로그 확대에서 "누가 했는지"를 바로 쓸 수 있다.
대시보드 액션 파일에서는 `runAction` 을 import 하지 않는다. 실수로 맨 것을 쓰면 눈에 띈다.

관리자 전용 액션은 `runAdminAction()` 을 쓴다.

## 로그인 유지

로그인 화면에 "로그인 상태 유지" 체크박스를 둔다.

- 체크: 인증 쿠키에 긴 만료(400일)를 준다. 브라우저를 닫아도 유지된다.
- 해제: 만료를 주지 않는다. 브라우저를 닫으면 풀린다.

선택을 `moa_persist` 쿠키에 남기고, 세션이 갱신될 때 쿠키 핸들러가 그 값을 보고 만료를 다시 정한다.
그러지 않으면 첫 갱신에서 선택이 사라진다.

## 화면

| 경로 | 접근 | 내용 |
|---|---|---|
| `/login` | 공개 | 아이디, 비밀번호, 로그인 유지 체크박스 |
| `/signup` | 공개 | 아이디, 표시 이름, 비밀번호. 가입 후 `/pending` |
| `/pending` | 로그인함·미승인 | "관리자 승인 대기 중". 로그아웃 버튼 |
| `/blocked` | 로그인함·차단됨 | "이용이 중지되었습니다". 로그아웃 버튼 |
| `/settings/users` | 관리자 | 사용자 관리 |

사이드바에 현재 사용자 이름과 로그아웃을 넣는다. 관리자에게만 사용자 관리 메뉴를 보인다.
대기자가 있으면 메뉴에 개수를 표시한다.

## 관리자가 할 수 있는 일

승인, 거절(삭제), 차단, 차단 해제, 비밀번호 초기화(관리자가 임시 비밀번호 지정),
관리자 권한 부여·회수, 계정 삭제.

**지켜야 할 선**
- 마지막 활성 관리자는 강등·차단·삭제할 수 없다. 그러면 아무도 승인할 수 없게 된다.
- 자기 자신은 차단·삭제할 수 없다.
- 모든 동작은 감사 로그에 남긴다. `entity_type: "user"`, 행위자 이름을 채운다.

## 기존 코드에 미치는 영향

- 대시보드 액션 11개 파일: `runAction` → `runAuthedAction` (55곳)
- `app/(dashboard)/layout.tsx`: `requireUser()` 추가, 사이드바에 사용자 영역
- `lib/actions/result.ts`: 주석의 "이 앱은 로그인이 없는 내부 도구" 문구를 고친다.
  오류 원인을 그대로 노출하는 근거가 바뀐다(이제 로그인한 직원만 본다).
- 공개 라우트와 `lib/db/*`: 변경 없음

## 검증 기준

1. 타입 체크, 린트, 기존 단위 테스트 144개 통과
2. 새 단위 테스트: 아이디 규칙, 승인 상태 전이, 마지막 관리자 보호, 내부 이메일 변환
3. 브라우저로 확인
   - 로그인 없이 `/campaigns` 접근 → `/login` 으로 감
   - 가입 → `/pending` 이 보이고 대시보드는 막힘
   - 관리자가 승인 → 대시보드 열림
   - 차단 → `/blocked` 로 감
   - 로그인 유지 체크 시 브라우저 재시작 후에도 유지, 해제 시 풀림
   - **공개 링크 6종은 로그인 없이 그대로 열림**
   - 로그아웃 후 서버 액션 직접 호출이 거부됨
4. 마지막 관리자 강등·삭제 시도가 막힘
