# 추가 개선 백로그 (2026-09-07)

`docs/REVIEW-2026-09-06.md` 검수와 `docs/FIX-LOG-2026-09-06.md` 수정을 마친 뒤, **아직 구현하지 않은** 부족한 점과 추가하면 좋을 항목을 우선순위 순으로 기록한다. 실제 생성 파일(PDF/PPTX/CSV)과 Gemini 호출까지 실검증한 상태를 기준으로 한다.

## 1. 외부 배포 전에 반드시 필요한 것

### 1-1. 데이터 백업
- **현황**: DB가 `.data/db.json` 파일 하나. 파일이 깨지거나 실수로 지우면 복구 수단이 없다.
- **할 일**: `lib/db/index.ts`의 `persist()`에서 저장 직전 파일을 `.data/backups/db-YYYYMMDD-HHmmss.json`으로 복사하고 최근 N개(예: 20개)만 유지. 복구 명령 또는 설정 화면에 "백업 목록/복원" 추가.
- **장기**: 데이터가 수 MB를 넘거나 동시 사용자가 늘면 SQLite(`better-sqlite3`)로 전환. `lib/db/index.ts`의 함수 시그니처를 유지하면 화면 코드는 손대지 않아도 된다.

### 1-2. 공개 폼 스팸 방어
- **현황**: `/apply/[token]`, `/pre-survey/[token]`, `/sns-intake/[token]`은 누구나 무제한 제출 가능.
- **할 일**: (1) 화면에 보이지 않는 허니팟 필드를 두고 값이 채워지면 조용히 거부, (2) IP·토큰 기준 제출 횟수 제한(예: 10분에 5회), (3) 같은 SNS 링크 중복 제출은 경고 후 허용(스펙대로 차단하지 않음).

### 1-3. 공개 토큰 재발급(회수)
- **현황**: 캠페인당 4개, SNS 계정당 2개 토큰이 생성 시 고정. 링크가 잘못 퍼져도 회수할 방법이 없다.
- **할 일**: `updateCampaign`/`updateSnsAccount`에 토큰 재발급 함수 추가, 캠페인 허브의 `TokenShareBox`와 SNS 계정 헤더에 "링크 재발급" 버튼(확인 다이얼로그 포함). 재발급 시 기존 링크는 즉시 404.

### 1-4. 로그인 (사용자 결정으로 보류 중)
- 테스트 편의를 위해 의도적으로 뺐다. 배포 시점에는 최소 `middleware.ts`로 대시보드 전체와 `/api/*/export?campaignId=` 경로에 비밀번호 쿠키를 요구할 것. 공개 토큰 라우트(`/apply`, `/pre-survey`, `/applicants`, `/seeding-sheet`, `/sns-intake`, `/sns-approval`)는 예외.

## 2. 실무 흐름에서 빠져 있는 것

### 2-1. SNS 승인 페이지에 시안 이미지/영상 첨부 (가장 큰 기능 추가)
- **현황**: 광고주가 캡션·해시태그 텍스트만 보고 승인한다. 실제 컨펌 용도로는 부족하다.
- **할 일**: `sns_contents`에 첨부 파일 목록 필드 추가, 파일 저장소(로컬 `.data/uploads/` 또는 S3 계열) + 업로드 액션, 대시보드 콘텐츠 모달에 업로드 UI, 승인 페이지에 이미지 갤러리. 파일 크기·형식 제한, 토큰 기반 접근 제어 필요. 하루 이상 걸리는 작업이라 별도 스펙으로 기획할 것.

### 2-2. 인플루언서 안내 메시지 템플릿
- **현황**: 선정 안내, 배송 안내, 콘텐츠 가이드 전달을 전부 수동으로 작성한다.
- **할 일**: 캠페인별 메시지 템플릿(선정/예비/배송/가이드/업로드 리마인드) 저장, 지원자 행에서 "안내문 복사" 버튼으로 이름·주소·기한을 치환해 클립보드에 복사. 발송 자동화는 범위 밖.

### 2-3. 지원자 판단 정보
- **현황**: 이름·SNS·연락처·국적·커스텀 답변만 있어 선정 근거를 남길 곳이 없다.
- **할 일**: `applicants`에 `follower_count`, `category`, `agency_memo` 추가. 지원폼에 팔로워 수(선택) 입력, 지원자 테이블에 메모 인라인 편집과 팔로워 순 정렬.

### 2-4. 마감 알림
- **현황**: D-day는 오버뷰 화면에만 있어 접속하지 않으면 모른다.
- **할 일**: 매일 아침 D-3 이내·지연 항목을 슬랙 웹훅 또는 이메일로 발송. `lib/overview/collect.ts`의 `collectOverviewItems()`를 그대로 재사용하면 되고, 실행은 Vercel Cron 또는 GitHub Actions 스케줄.

### 2-5. 삭제·보관
- **현황**: 캠페인과 SNS 계정은 만들 수만 있고 지우거나 보관할 수 없다. 종료 항목이 목록에 계속 쌓인다.
- **할 일**: 캠페인 `status=completed`, SNS `status=ended` 항목을 기본 목록에서 접고 "보관 보기" 필터 제공. 삭제는 하위 데이터(지원자·시딩·행사·보고서) 연쇄 삭제와 확인 다이얼로그 포함.

### 2-6. 변경 이력(감사 로그)
- **현황**: 지원자 선정 상태 변경 주체·시각만 기록된다.
- **할 일**: SNS 승인/수정요청, 관리시트 단계 변경, 행사 상태 변경을 `audit_log` 컬렉션에 `{who, what, before, after, at}`로 기록하고 각 상세 화면에 "이력" 탭 표시. 광고주와의 분쟁 대비.

### 2-7. 목록 규모 대응
- **현황**: 지원자·콘텐츠 목록이 전부 한 화면에 렌더링된다. 수백 건이 넘으면 느려진다.
- **할 일**: 지원자 테이블 페이지네이션 또는 가상 스크롤, 정렬(신청일·상태·팔로워), 캠페인 목록 검색.

## 4. 개발 환경·운영

### 4-1. CI
- GitHub Actions에 `npm ci` → `typecheck` → `lint` → `test` → `test:e2e`(Playwright 브라우저 설치 포함)를 걸어 PR/푸시마다 실행. Gemini가 다음 수정을 했을 때 회귀를 바로 잡을 수 있다.

### 4-2. 에러 모니터링
- 서버 에러가 콘솔에만 남는다. Sentry 무료 플랜 연동(`@sentry/nextjs`)으로 서버 액션·라우트 에러 수집.

### 4-3. 디자인 토큰 정리
- 모든 화면이 hex 하드코딩(`bg-[#131418]` 등) 위에 `globals.css`의 `!important` 덮어쓰기로 라이트 모드를 만든다. 새 화면에서 다른 hex를 쓰면 라이트 모드가 깨진다. 스펙의 토큰(`bg-bg`, `bg-surface`, `text-textMuted` …)으로 일괄 치환하고 덮어쓰기 규칙 삭제. 급하지 않지만 화면이 더 늘기 전에.

### 4-4. AI 호출 비용·안정성
- 현재 호출당 2~4초, 실패 시 폴백 문구. 같은 입력의 반복 호출을 줄이려면 최근 결과 캐시(입력 해시 → 결과, 24시간) 고려. 프롬프트가 5개 파일에 흩어져 있으니 `lib/ai/prompts.ts`로 모으면 톤 조정이 쉬워진다.

### 4-5. 저장소 정리
- `app/(dashboard)/design-preview/`(테마 시안), `docs/sql/`(Supabase용, 현재 미사용), `.agents/`(3.7MB 스킬 파일)는 사용자 판단으로 유지 중. 배포 번들에서 제외하거나 정리할지 결정 필요.
