# 실사용 직전 작업 정리

**기간** 2026년 9월 14일 저녁 6시 ~ 9월 15일 오전 9시
**커밋** 20개 · **파일** 132개 변경 (8,973줄 추가 / 1,073줄 삭제)
**검증** 단위 테스트 193개 통과 · e2e 49개 통과 · 빌드 통과 · 린트 오류 0건

밤사이 세 가지를 했습니다. **로그인과 권한 체계를 처음부터 만들었고**, **서비스 이름을 RB Global로 바꿨고**, **실사용 전 보안 점검을 해서 나온 구멍을 막았습니다.**

---

## 1. 로그인과 권한 (저녁 6시 ~ 밤 12시)

그전까지는 주소를 아는 사람이면 누구나 대시보드에 들어올 수 있었습니다.

### 아이디·비밀번호 로그인

이메일을 쓰지 않습니다. 아이디와 비밀번호만 씁니다. 내부적으로는 아이디를 가짜 이메일 주소로 바꿔 인증 서버에 저장하지만 사용자는 그것을 보지도 입력하지도 않습니다.

**가입해도 바로 못 들어옵니다.** 관리자가 승인해야 합니다. 승인 전에는 대기 화면만 보입니다.

**로그인 상태 유지** 체크박스가 있습니다. 켜면 브라우저를 닫아도 로그인이 남고, 끄면 브라우저를 닫을 때 풀립니다. 공용 PC를 쓸 때를 위한 것입니다.

### 등급 세 가지

| 등급 | 할 수 있는 일 |
|---|---|
| 대표 관리자 | 전부. 등급 변경, 활동 기록 열람, 초대 링크 발급 |
| 관리자 | 업무 전체 + 직원의 승인·차단·비밀번호 초기화 |
| 직원 | 업무 전체 |

관리자는 직원만 다룰 수 있습니다. 다른 관리자나 대표는 건드리지 못합니다. 등급을 바꾸는 것은 대표 관리자만 할 수 있습니다.

**잠기지 않도록 막아둔 것들**이 있습니다. 마지막 남은 대표 관리자는 강등도 차단도 삭제도 되지 않습니다. 아무도 자기 자신을 차단하거나 삭제할 수 없습니다. 이게 없으면 실수 한 번으로 아무도 들어갈 수 없는 상태가 됩니다.

### 차단과 삭제

| | 차단 | 삭제 |
|---|---|---|
| 계정 | 남음 | 사라짐 |
| 되돌리기 | 됨 | 안 됨 |
| 아이디 | 계속 점유 | 다른 사람이 쓸 수 있음 |
| 기록 | 남음 | 남음 |

퇴사자는 차단이 기본입니다. 되돌릴 수 있기 때문입니다.

### 내 정보 화면

누구나 자기 이름과 비밀번호를 바꿀 수 있습니다. 비밀번호를 바꾸려면 지금 쓰는 비밀번호를 함께 넣어야 합니다. 로그인한 브라우저를 잠깐 빌린 사람이 계정을 통째로 가져가는 것을 막기 위해서입니다.

## 2. 활동 기록 (저녁 8시 ~ 밤 12시)

데이터를 바꾸는 모든 작업이 자동으로 기록됩니다. 담당자가 따로 적지 않아도 로그인 정보에서 이름을 가져와 붙입니다.

지금 **43가지 작업**이 기록됩니다. 캠페인·지원자·시딩·행사·SNS·보고서·계정 전 영역입니다.

**보기만 한 것은 기록하지 않습니다.** 열람까지 남기면 하루에 수백 줄이 쌓여 정작 찾아야 할 한 줄이 묻힙니다. 로그인·로그아웃, 파일 내려받기, AI 초안 생성도 남기지 않습니다. 데이터를 바꾸지 않기 때문입니다.

**기록은 대상보다 오래 삽니다.** 캠페인을 지우면 그 안의 데이터는 사라지지만 "누가 언제 지웠다"는 남습니다. 삭제할 때는 지우기 전에 먼저 기록합니다.

**대표 관리자만 봅니다.** 처음에는 관리자까지 열었다가 좁혔습니다. 동료의 작업 내역을 들여다보는 창이기도 해서, 보는 사람이 늘수록 기록의 의미가 옅어집니다. 메뉴를 숨기는 데 그치지 않고 주소를 직접 입력해도 막힙니다.

이 내용을 대표 관리자께 보낼 세 쪽짜리 PDF로 따로 만들어 뒀습니다. `docs/RB-Global-활동기록-안내.pdf`

## 3. 이름 변경 (밤 11시 ~ 12시)

MOA에서 **RB Global**로 바꿨습니다. 로고, 아이콘, 화면 문구, 브라우저 탭 제목, 앱 설치 정보까지 전부입니다.

글꼴은 Inter ExtraBold로 정했습니다. 글꼴 파일을 저장소에 담아서 외부에 요청하지 않고, 네트워크와 무관하게 같게 보입니다.

앱 아이콘은 RB 두 글자입니다. 작은 아이콘은 글자를 키우고 테두리를 뺐습니다. 브라우저 탭에서 16픽셀로 줄었을 때 테두리가 글자 쓸 자리를 그대로 빼앗기 때문입니다.

**내부 식별자는 바꾸지 않았습니다.** 계정이 저장된 주소(`moa.local`)를 바꾸면 기존 계정이 전부 로그인하지 못합니다. 사용자에게 보이지 않는 값이라 바꿀 이유도 없습니다.

## 4. 보안 점검 (새벽 1시 ~ 오전 9시)

다섯 갈래로 나눠 전수 점검했습니다. 인증·권한, 공개 라우트, 데이터 안전, 기능, 배포 설정입니다.

### 가장 큰 구멍: 파일 내려받기

**누구나 지원자 명단을 엑셀로 받을 수 있었습니다.**

대시보드 화면과 저장 동작은 잘 막혀 있었는데, 파일을 내려받는 아홉 개 경로가 "쿠키가 있는가"만 보고 있었습니다. 가입 신청만 하면 승인 전이라도 쿠키가 생깁니다. 캠페인 주소 하나만 알면 지원자 전원의 이름·연락처·배송지가 담긴 파일을 받을 수 있었습니다. 차단된 퇴사자도 남은 쿠키로 같은 일을 할 수 있었습니다.

승인된 계정만 통과하도록 아홉 곳을 막았습니다. 앞으로 새 경로를 만들며 빠뜨리면 테스트가 잡습니다.

### 두 번째: 광고주에게 배송지가 갔다

관리시트 공유 화면과 내보내기 파일에서 **배송지와 에이전시 내부 비고가 그대로 나가고 있었습니다.**

이것은 두 번에 걸쳐 고쳤습니다. 처음에 지원자 정보만 씻었는데, 배송지는 시딩 기록에도 따로 들어 있었습니다. 절반만 고친 상태였습니다. e2e 테스트를 쿠키 없는 브라우저로 돌리도록 바꾸면서 드러났습니다. 전에는 로그인한 상태로 확인하고 있어서 "로그인 없이도 보이는가"를 애초에 검증하지 못하고 있었습니다.

### 나머지 보안 항목

| 항목 | 내용 |
|---|---|
| 보안 헤더 | 없었습니다. 승인·선정 화면을 남의 사이트가 프레임으로 덮을 수 있었습니다 |
| 로그인 실패 제한 | 메모리로 세고 있어 실제로는 아무것도 막지 못했습니다. DB로 옮겼습니다 |
| 차단 | 상태만 바꾸고 세션은 살려뒀습니다. 이제 인증 계정까지 잠급니다 |
| 공개 폼 오류 | DB 내부 이름이 그대로 나갔습니다. 외부인에게는 고정 문구만 |
| 공유 링크 토큰 | 44비트였습니다. 128비트로 올렸습니다 |
| 활동 기록 조회 | 화면은 대표 전용인데 뒷단은 관리자까지 열려 있었습니다 |
| 삭제 권한 | 직원도 캠페인을 영구 삭제할 수 있었습니다. 관리자 이상으로 |
| 웹훅 테스트 | 유일하게 인증 없이 실행됐습니다 |
| 웹훅 주소 | 로그에 통째로 찍혔습니다. 주소 자체가 자격증명입니다 |

### 데이터 안전

**백업이 조용히 실패할 수 있었습니다.** 배포에 저장소 연결이 빠지면 임시 디스크에 쓰고 성공한 것처럼 보였습니다. 그 파일은 다음 요청 때 사라집니다. 이제 실패로 표시됩니다.

**백업에 계정 정보가 없었습니다.** 넣었습니다. 로그인 비밀번호 자체는 Supabase가 보관합니다.

**백업이 천 행을 넘으면 빠지거나 겹칠 수 있었습니다.** 페이지를 나눠 읽는데 순서가 고정돼 있지 않았습니다.

**백업 사본이 한 곳뿐이었습니다.** 로컬로 내려받는 명령을 추가했습니다. 절차는 `docs/ops-backup.md`에 적었습니다.

**두 사람이 같은 기획안을 열면 나중 저장이 앞 것을 덮어썼습니다.** 이제 거부하고 새로고침을 안내합니다.

## 5. 가입 방식 (오전 7시 ~ 9시)

두 번 바뀌었습니다. 처음에는 모두가 같은 8자 코드를 쓰는 방식으로 만들었다가, **1회용 초대 링크**로 갈아탔습니다.

코드는 한 번 새면 바꿀 때까지 계속 유효합니다. 단톡방에 올라가면 그대로 퍼지고, 누가 그 코드로 들어왔는지 알 방법도 없습니다.

지금은 대표 관리자가 사람마다 링크를 하나씩 만들어 보냅니다. **링크는 계정이 만들어지는 순간 죽습니다.** 전달해도 두 번 쓰이지 않습니다. 기한은 72시간입니다.

만료 시간보다 1회용인 것이 핵심입니다. 한 번 쓰면 죽으므로 기한을 사흘로 잡아도 위험하지 않습니다. 10분짜리로 만들면 카톡으로 보내는 사이에 죽어서 재발급만 반복하게 됩니다.

가입 주소로 그냥 들어가면 안내만 보입니다. 폼 자체가 없습니다.

## 6. 화면과 사용성

| 고친 것 | 이유 |
|---|---|
| 승인 대기 배너 | 사이드바 배지뿐이라 폰에서는 메뉴를 열어야 알 수 있었습니다 |
| 시각 표시 | 배포 환경에서 영문으로 아홉 시간 어긋났습니다 |
| 삭제 확인창 | 무엇이 함께 사라지는지 정확히 적습니다 |
| 저장 중 이동 | 눌러 놓고 넘어가면 요청이 끊겨 DB에 안 남았습니다 |
| 오류 화면 | 영문 기본 화면이 나왔습니다 |
| 종료된 캠페인 링크 | 끝난 뒤에도 옛 링크가 고객사 데이터를 계속 내보냈습니다 |
| 404 화면 | 옛 공유 링크를 연 광고주가 영문 화면을 봤습니다 |
| 로그인 화면 | 비밀번호 분실 시 안내가 없었습니다 |
| 첫 화면 빈 상태 | 다음에 뭘 해야 할지 알려주는 링크가 없었습니다 |

**저장 중 이동**은 조금 다르게 만들었습니다. 그냥 막으면 사용자는 클릭이 무시당한 줄 알고 다시 누릅니다. 그래서 가려던 곳을 기억했다가 저장이 끝나면 대신 이동시킵니다. 저장 자체는 75밀리초라 체감되지 않습니다.

**가이드에 "로그인이 없습니다"라고 적혀 있었습니다.** 지금과 정반대입니다. 고치고 계정·등급·초대 링크·비밀번호 분실 안내를 넣었습니다.

## 7. 테스트

| | 어제 저녁 | 지금 |
|---|---|---|
| 단위 테스트 | 약 150개 | 193개 |
| e2e | 실행 불가 | 49개 통과 |

**e2e는 매번 실패하고 있었습니다.** 없어진 샘플 데이터를 참조하고 로그인이 없던 시절을 전제하고 있었습니다. 되살렸습니다.

공개 링크 검증을 **쿠키 없는 브라우저로 분리**한 것이 중요합니다. 로그인한 상태로 확인하면 "로그인 없이도 열리는가"를 검증하지 못합니다. 이 때문에 배송지 유출을 놓치고 있었습니다.

CI는 e2e를 단위 테스트 뒤에 돌리고 순서를 세웁니다. 둘이 같은 테스트 DB를 쓰기 때문입니다.

## 8. 알려진 문제 처리 (오후)

공개 직전 점검에서 나왔지만 미뤄뒀던 항목을 처리했습니다.

| 문제 | 어떻게 됐나 |
|---|---|
| **백업이 멈춰도 아무도 모름** | 대시보드 첫 화면에 **대표 관리자만 보는** 경고 배너를 넣었습니다. 마지막 백업이 48시간을 넘으면 "마지막 DB 백업이 N일 전입니다" 가 뜹니다. 정상이면 아무것도 안 보입니다. 크론 성공 여부가 아니라 **결과물(백업 파일)** 을 보므로 실패 원인이 무엇이든 잡힙니다 |
| **캠페인 삭제가 버튼 한 번** | 캠페인 이름을 그대로 옮겨 적어야 삭제 버튼이 열립니다. 무엇이 함께 지워지는지도 대화상자에 사실대로 적었습니다 |
| **복원 명령이 기본으로 운영을 겨냥** | 데이터를 바꾸는 작업은 이제 `--prod` 를 손으로 적어야 실행됩니다. `--test` 한 단어를 빠뜨려 운영을 지우는 사고를 막습니다. 미리보기는 그대로입니다 |
| **테스트가 운영 DB를 비울 수 있는 마지막 틈** | 기존 검사는 환경변수끼리 비교하는 방식이라, `.env.local` 을 통째로 운영 값으로 덮으면 전부 통과했습니다. 이제 **DB 안에 표식 테이블(`test_db_marker`)** 이 있어야만 truncate 합니다. 운영에는 없으므로 주소를 아무리 잘못 넣어도 한 줄도 안 지워집니다 |
| **사전조사 재제출이 흔적 없이 덮어씀** | 덮어쓰기는 그대로 두되(오타 수정은 정상 사용), 재제출일 때만 활동 기록에 남깁니다. 답변 본문·개인정보는 담지 않고 "몇 문항이 바뀌었나"만 남깁니다 |
| **저장소 진단 화면을 전 직원이 봄** | 관리자 이상만 봅니다. 키는 원래 안 담겼지만 저장소 구성과 테이블 규모가 드러납니다 |
| **인메모리 횟수 제한이 서버리스에서 무력** | 공개 폼 제출과 AI 추천 제한을 전부 DB(`auth_throttle`)로 옮기고 `lib/security/rateLimit.ts` 를 지웠습니다. 메모리에 세면 요청마다 초기화돼 사실상 제한이 없었습니다 |
| **Next.js 16.3.3** | 16.3.5 로 올렸습니다 |

## 9. 미뤄뒀던 나머지도 처리 (오후 늦게)

위에서 "문서에만 적어두자" 했던 네 가지를 결국 다 고쳤습니다.

| 문제 | 어떻게 됐나 |
|---|---|
| **CSP 가 스크립트를 막지 못함** | 요청마다 난수(nonce)를 만들어, 그 값을 단 스크립트만 실행되게 했습니다. 공격자가 페이지에 `<script>` 를 밀어 넣어도 난수를 맞출 수 없어 실행되지 않습니다. 실제로 운영 빌드를 띄워 브라우저에서 확인했습니다 — 정상 화면은 그대로 뜨고(테마 깜빡임도 없음), 일부러 심은 가짜 XSS 는 차단됐습니다. 대신 모든 페이지가 요청마다 렌더됩니다(원래 `/signup` 말고는 전부 그랬습니다) |
| **공용 질문 템플릿 동시 수정** | 사전조사·SNS 인테이크 두 템플릿에 낙관적 잠금을 걸었습니다. 행사 운영안·SNS 제안서가 쓰던 것과 같은 방식입니다. 남이 먼저 저장했으면 덮어쓰지 않고 "다른 사람이 먼저 저장했습니다. 새로고침한 뒤 다시 저장해주세요" 로 막습니다. 화면→액션→DB 왕복까지 연결했고 테스트 2건을 추가했습니다 |
| **의존성 중간 취약점 2건** | 0건이 됐습니다. exceljs 가 쓰는 `uuid` 는 `overrides` 로 고친 버전을 강제했고(엑셀 내보내기 테스트로 확인), vitest 는 3 → 5 로 올렸습니다. `@types/node` 도 20 → 24 로 맞췄습니다(실행 환경이 원래 Node 24 였습니다) |
| **린트 경고 12건** | 0건이 됐습니다. 안 쓰는 import 는 지우고, `<img>` 5곳은 `next/image` 로 바꾸지 않고 규칙을 끄되 **왜 안 바꾸는지**를 주석에 적었습니다(비공개 시안 파일이라 최적화 캐시가 권한 우회 경로가 됩니다) |

작업 중 테스트 하나에서 빠진 단언도 하나 찾아 되살렸습니다(`phase3.test.ts` 의 첨부 id 대조).

남은 항목은 `docs/HANDOFF.md` 9장 "아직 고치지 않은 것" 에 있습니다. `style-src` 의 `unsafe-inline`,
최후의 오류 화면(`/_global-error`), 사전조사 응답 1건 구조, 업로드 파일 백업 — 네 가지이고 모두 이유를 적어뒀습니다.

## 10. 공개 페이지(광고주·지원자) 보안 점검

로그인 뒤 화면과 위협 모델이 달라서 따로 봤습니다. 공개 링크는 **토큰만 알면 누구나 열고**, 그 토큰은 메일·카톡으로 퍼집니다.

### 고친 것

| 문제 | 어떻게 됐나 |
|---|---|
| **AI 입력 길이에 상한이 없었다** | 가장 큰 구멍이었습니다. 링크를 가진 사람이 한 번에 4MB 짜리 글을 AI 에 밀어 넣을 수 있었고, 링크당 하루 2,880회까지 가능해서 **하루 200만 원대**까지 요금이 나올 수 있었습니다. 프롬프트를 만드는 자리에서 2,000자로 자릅니다 |
| **AI 응답이 깨지면 횟수를 돌려줬다** | 모델은 이미 불러 돈이 나간 뒤인데 횟수를 환불해서, 응답이 깨지도록 유도하는 입력을 반복하면 질문당 3회 상한을 무한히 우회할 수 있었습니다. 이제 **모델을 부르지도 못했을 때만** 돌려줍니다 |
| **횟수 제한을 토큰 확인 전에 셌다** | 제한 키에 토큰이 들어가는데 확인을 안 해서, 아무 문자열이나 보낼 때마다 제한표에 새 행이 쌓였습니다. 키가 매번 달라 **어떤 제한에도 안 걸렸고**, 그것만으로 DB 용량을 채워 로그인까지 멈출 수 있었습니다. 공개 액션 5곳 전부 순서를 뒤집었습니다 |
| **검색엔진이 공개 링크를 색인할 수 있었다** | `/robots.txt` 가 로그인 화면으로 튕겨서 크롤러는 "robots.txt 가 없다"로 읽었고, 페이지에 `noindex` 도 없었습니다. 전체 차단하는 robots.txt 를 넣고 모든 페이지에 `noindex` 를 걸었습니다 |
| **지워진 질문의 옛 답변이 광고주에게 갔다** | 지원폼에서 질문을 지워도 기존 지원자의 답은 DB 에 남습니다. 화면은 현재 질문만 그렸지만 **페이지 소스에는 옛 답이 전부 실려** 있었습니다. 지난 세 번의 사고와 같은 모양입니다. 이제 현재 질문의 답만 내보냅니다 |
| **개인정보 무해화가 "지우기 목록"이었다** | `Applicant` 에 새 필드가 생기면 아무도 손대지 않아도 광고주에게 나가는 구조였습니다. 세 번의 사고가 난 진짜 원인입니다. **골라 담기**로 바꿔 새 필드의 기본값이 '안 나감'이 되게 했고, 키 전수 대조 테스트가 이 구조를 지킵니다 |
| **계약 종료일이 링크를 닫지 않았다** | 사람이 손으로 상태를 "계약종료"로 바꾸기 전까지, 계약이 끝난 광고주가 공개 전 시안을 계속 보고 승인까지 할 수 있었습니다. `ends_on` 은 저장만 되고 판정에 안 쓰였습니다. 이제 종료일 다음날부터 닫힙니다 |
| **승인 링크에만 횟수 제한이 없었다** | 다른 공개 폼 셋과 같은 제한을 걸었습니다 |
| **허니팟이 티가 났다** | 스팸으로 걸러도 `"spam_filtered"` 라는 고정값을 돌려줘서, 봇이 한 번 찔러보면 어느 칸이 함정인지 알아냈습니다. 진짜 저장과 같은 모양의 값을 돌려줍니다 |
| **지원자 이름으로 슬랙 전체 멘션이 가능했다** | 이름 칸에 `<!channel>` 을 적으면 대행사 슬랙 채널 전원이 호출됐습니다. 멘션으로 안 읽히게 바꿉니다 |
| **공개 경로 접두사 두 개가 너무 넓었다** | `/api/applicants/export` 가 접두사라 `…/export-all` 같은 주소까지 미리 열어두는 셈이었습니다(지금은 그런 라우트가 없어 샌 것은 없습니다). 정확히 일치로 바꿨습니다 |
| **같은 id 의 확장자만 바꿔 남의 시안을 가릴 수 있었다** | 파일을 찾을 때 접두사로 시작하기만 하면 아무거나 골라서, `.gif` 를 올리면 `.jpg` 보다 먼저 잡혔습니다. 정확한 확장자 한 칸만 인정합니다 |
| **초대 링크 되돌리기가 조건이 없었다** | 가입 실패 시 링크를 되돌리는데, 그 사이 다른 사람이 정상 소비한 경우까지 되살릴 수 있었습니다 |

### 확인했고 문제 없던 것

주요한 것만 적습니다. 광고주에게 나가는 **모든 출구**(화면·서버 액션 반환값·CSV·엑셀)를 세어 각각 무해화를 거치는지 대조했고, 끝난 캠페인이 화면과 파일 양쪽에서 닫히는 것, 토큰이 전부 128비트 이상 난수인 것, 광고주가 남의 캠페인 자원을 건드릴 수 없는 것, `/api/media` 가 다른 계정 토큰·승인 전 시안·종료 계정을 모두 막는 것, CSV·엑셀 수식 주입이 막힌 것, 공개 응답이 CDN 에 캐시되지 않는 것, 오픈 리다이렉트가 막힌 것을 확인했습니다.

배포된 사이트에 직접 요청을 보내 보안 헤더·보호 경로·잘못된 토큰 응답·업로드 토큰 발급도 확인했습니다.

### 판단이 필요해서 남긴 것

셋 중 둘은 상의 후 처리했고, 하나만 남겼습니다.

| 항목 | 결정 |
|---|---|
| **중복 배지** | 광고주에게는 **SNS 중복만** 보냅니다. 연락처 중복은 대행사만 봅니다 — 가족·지인이 각자 계정으로 지원한 정상 케이스까지 관계가 드러나기 때문입니다 |
| **내려받기 기록** | 광고주가 토큰으로 파일을 받아가면 활동 기록에 남깁니다. **"언제·무엇·몇 건" 만** 남기고 IP·브라우저·토큰은 남기지 않습니다. 광고주는 계정이 없어 IP 로도 "누구" 를 알 수 없으니, 알 수 없는 것을 적으려고 개인정보를 더 모으지 않습니다. 쓸모는 "평소와 다른가" 입니다 |
| **커스텀 질문 공유 여부** | 질문마다 **"광고주 공개" 체크박스**를 넣었습니다 (아래) |

### 커스텀 질문에 "광고주 공개" 체크박스

전에는 지원폼에 질문을 추가하면 **지원자가 그 칸에 써 넣는 내용이 무조건** 광고주 화면·CSV·엑셀로 갔습니다. 질문 제목이 아니라 지원자가 쓴 답입니다. "카카오톡 ID", "생년월일", "상세 주소" 같은 걸 물으면 전원의 값이 그대로 나갔고, 편집 화면에는 그렇게 된다는 안내가 한 줄도 없었습니다. 특히 **주소는 고정 칸(배송지)을 막아뒀는데 커스텀 질문으로 물으면 그 방어가 그대로 우회**됐습니다.

이제 질문마다 켜고 끕니다.

```
1  [왜 이 제품을 써보고 싶나요  ] [단답형 ▾] □필수  ☑광고주 공개
2  [카카오톡 ID                ] [단답형 ▾] ☑필수  □광고주 공개
```

- **새 질문은 "비공개" 가 기본입니다.** 반대로 두면 체크 해제를 깜빡하는 순간 전원의 값이 나갑니다. 보여줄 질문은 만들 때 한 번 눌러주세요.
- **표시가 없는 질문도 "안 보임" 으로 읽습니다.** 모르면 가립니다. 그래서 이 기능 이전에 만든 질문은 배포 후 광고주 화면에서 사라집니다(운영에는 테스트 질문 1개뿐이라 영향 없음).
- 질문 목록 위에 **"광고주에게 보이는 질문 N개 · 우리만 보는 질문 M개"** 요약이 뜹니다. 질문이 늘어도 어느 게 나가는지 한눈에 보입니다.
- 광고주에게 나가는 **다섯 곳 전부**에 걸었습니다 — 지원자 화면, 상태변경 액션 응답, 지원자 CSV·엑셀, 관리시트 화면, 관리시트 CSV·엑셀.

구현 중에 `saveFormConfig` 가 질문을 다시 조립하면서 **새 칸을 버리는** 것을 잡았습니다. 체크박스를 눌러도 저장이 안 되는 상태였는데, 타입 검사로는 안 잡히고 **DB 에 저장했다 다시 읽어보고서야** 나왔습니다.

### 점검 뒤에 확인한 두 가지

점검 직후에는 "대시보드에서 하실 일" 로 두 가지를 적었는데, 확인해 보니 하나는 이미 끝났고 하나는 **애초에 할 일이 아니었습니다.**

- **Supabase anon 가입**: 껐습니다. 앱은 이 기능을 쓰지 않습니다(관리자 권한으로 계정을 직접 만듭니다).
- **Vercel Blob public 업로드 막기**: **그런 설정은 없고, 막을 필요도 없었습니다.** 공개/비공개는 **저장소를 만들 때** 정해지는데 현재 저장소가 Private 입니다. 비공개 저장소는 읽기·쓰기 모두 인증을 요구하고, 파일 주소도 `…private.blob.vercel-storage.com` 이라 공개 주소가 아예 나오지 않습니다. 제가 존재하지 않는 설정을 찾게 만들었습니다.

  다만 **저장소를 새로 만들 일이 생기면 반드시 Private 으로** 만들어야 합니다. 브라우저 직접 업로드 토큰에는 공개/비공개를 실을 수 없어서, **저장소가 Private 이라는 사실이 유일한 방어선**입니다. `docs/HANDOFF.md` 의 "이미 막아둔 것" 에 적어뒀습니다.

## 11. 기능 점검 (마지막)

보안 렌즈로 세 번 봐도 안 나오던 것들이 있었습니다. **"눌렀는데 아무 일도 안 일어난다"** 쪽으로
렌즈를 바꾸니 나왔고, 세 갈래 점검이 독립적으로 **같은 원인 셋**을 지목했습니다 — 에러를 배너로만
띄워 모달 뒤에 가리는 것, `useState` 후 재동기화 누락, 타입 단언이 컴파일러 확인을 꺼 둔 것.
무작위가 아니라 **몇 개의 패턴이 여러 곳에 복제된 것**이었습니다.

### 데이터가 망가지던 것

**안내문을 "기본 템플릿으로 저장" 하면 개인정보가 박제됐습니다.** 모달의 글은 `{{이름}}` 이 치환된
완성 메시지인데 그걸 그대로 템플릿으로 저장했고, 치환 항목에 **연락처와 배송주소**가 있었습니다.
한 번 누르면 그 지원자의 전화번호·주소가 캠페인 템플릿에 박히고 **그 다음부터 모든 지원자가 남의
주소가 적힌 안내문**을 받았습니다. 화면에서 되돌릴 방법도 없었습니다. 아직 아무도 안 눌렀습니다.

### 기능이 아예 안 되던 것

- **선택형 문항에 쉼표가 안 쳐져 선택지를 2개 이상 만들 수 없었습니다.** 붙여넣기는 되기 때문에
  만든 사람은 동작한다고 착각합니다.
- **안내 메시지 템플릿 5개 중 2개가 빈 버튼**이었고 눌러도 내용이 안 채워졌습니다.
- **마지막 페이지에서 상태를 바꾸면 빈 표에 갇혔습니다.** 페이지 버튼까지 사라져 빠져나올 수
  없었습니다.

### 나머지 고친 것

탭 복귀 시 목록 갱신(7개 화면), 탭 전환 시 미저장 편집 소실, 내려받기 실패가 JSON 날것으로
보이던 것, AI 남은 횟수 표시 어긋남, 낙관적 갱신 롤백이 남의 변경까지 되돌리던 것, 관리시트
잠긴 행에 이유가 없던 것, 행사 정보 수정 취소가 안 먹던 것, SNS 모달 에러가 가려지던 것,
PPT 교체 무반응, 대표 관리자 강등 표시 오류, 업로드 완료 판정이 화면마다 다르던 것,
종료된 캠페인에 "접수중" 배지.

`docs/sql/` 은 **다른 프로젝트 스키마**여서 지웠습니다(`sns_url` vs `sns_link`,
캠페인 상태 3개 vs 6개). 실수로 운영에 돌리면 스키마가 깨집니다. git 이력에 남아 있습니다.

### 남긴 것

작은 사용성 항목도 이어서 처리했습니다. 17건을 확인해 16건 고쳤습니다.

- **알림이 안 보이던 곳 8건** — 전부 배너만 있고 모달 뒤나 스크롤 밖이었습니다. 배너는 두고
  토스트를 같이 띄웁니다. 그중 **지원 신청 폼에는 토스트가 하나도 없었습니다** — 인플루언서가
  쓰는 가장 중요한 공개 화면인데, 동의 체크를 빠뜨리면 폼 맨 아래에서 눌렀는데 에러는 맨 위에
  떠서 버튼이 죽은 것처럼 보였습니다.
- **로딩 표시 4건** — 모바일 메모 저장, 중복 지원 계속 제출, PPT 템플릿 삭제·되살리기, 행사 삭제
- **토스트 퇴장 애니메이션** — 숫자 셋이 따로 놀아 퇴장이 시작조차 못 했습니다
- **안내문 모달 ESC** — 배경 클릭은 일부러 뺐습니다(편집 중 드래그하다 밖에서 손을 떼면 날아감)
- **클립보드 실패 `alert()`** → 토스트
- **행사 목록 "취소됨" 필터** — 탭 둘 합이 "전체" 와 안 맞았습니다
- **방문 인원수 0** — 칸을 비울 방법 자체가 없었고, 막히는 이유도 화면에 안 남았습니다.
  서버 기준(빈 값=1명, 1~20)에 맞췄습니다
- **직원에게 캠페인 삭제 버튼 감춤** — 이름을 다 옮겨 적고 누른 뒤에야 거부당했습니다.
  **화면 편의일 뿐 방어는 서버 액션에 그대로 있습니다**

확인 중에 **계약 종료일이 지났는데 대시보드만 "운영중" 이라고 표시하던 것**도 찾아 고쳤습니다.
공개 링크는 이미 닫혀 있었는데 화면이 반대말을 하고 있었습니다.

**안 고친 1건**: 초대자 메모 칸. 고치려면 제어 입력으로 바꿔야 하는데, 그러면 옆 행에 메모를
치던 중 탭 복귀 갱신에 입력이 날아갑니다. 지금보다 나쁩니다.

### 초대자 메모 — 덮어쓰지 않고 알리는 쪽으로

행사 초대 명단의 메모 칸은 **비제어 입력**이라, 한 번 타이핑한 칸은 서버에서 새 값이 내려와도
화면이 안 바뀌었습니다(건드리지 않은 칸은 정상 갱신됩니다).

제어 입력으로 바꾸면 그 문제는 사라지지만 **더 나쁜 것**이 생깁니다 — 이 화면은 탭 복귀 뒤
자동 갱신이 돌기 때문에, 옆 행에 메모를 치던 중 갱신이 걸리면 **치던 글자가 덮여 사라집니다.**

그래서 **아무것도 자동으로 덮어쓰지 않습니다.** 내가 손댄 칸의 서버 값이 그 사이 바뀌면
그 행에만 안내를 띄우고, [서버 값 쓰기] / [내 것 유지] 중 사람이 고릅니다. 운영안·제안서의
낙관적 잠금과 같은 사고방식입니다.

### scripts 타입 검사

`scripts/*.mjs` 는 기본 tsconfig 의 `include` 밖이라 **타입 검사를 전혀 안 받고 있었습니다.**
마이그레이션·백업처럼 되돌리기 어려운 코드가 거기 있습니다.

켜 보니 70건이 나왔는데 **55건은 "매개변수에 타입이 없다"** — 버그가 아니라 주석 다는 일이라
그 검사만 껐습니다. 남은 **13건은 전부 진짜**였습니다:

- `pg` 의 `rowCount` 가 null 일 수 있는데 `> 0` 으로 바로 비교 (5건)
- **복원 실패 사유를 찍는 자리에서 `err.message`** — Error 가 아닌 것이 던져지면 `undefined`
  만 찍힙니다. 데이터를 되돌리다 실패했는데 이유를 모르게 됩니다 (4건)
- 가드는 있는데 함수 안에서는 컴파일러가 못 보던 것 (4건)

전부 고쳐 0건이 됐고, `npm run typecheck:scripts` 와 **CI 단계**로 연결했습니다.

## 백업 상태 (2026-09-15 확인)

**Supabase 무료 요금제에는 자동 백업이 없습니다.** 그래서 매일 새벽 3시에 도는 우리 백업이
유일한 방어선입니다. 다음을 알고 계셔야 합니다.

| 잃었을 때 | 되살릴 수 있나 |
|---|---|
| 캠페인·지원자·SNS·행사·활동 기록 | 됩니다. 매일 백업에 들어 있습니다 |
| 계정 정보(아이디·이름·등급·승인 상태) | 됩니다. 백업에 들어 있습니다 |
| **로그인 비밀번호** | **안 됩니다.** Supabase만 갖고 있습니다 |
| 업로드한 시안 파일·PPT 템플릿 | 안 됩니다. 파일은 백업 대상이 아닙니다 |

비밀번호가 백업에 없는 것은 의도한 것입니다. 비밀번호를 파일로 빼두면 그 파일이 곧 새로운
위험이 됩니다. Supabase 프로젝트를 통째로 잃는 최악의 경우, 계정 몇 개를 다시 만들고 새
비밀번호를 나눠주면 됩니다. 사람 수가 적어 감당할 수 있는 일입니다.

**권장 절차**: 주 1회 `npm run db:backup` 을 손으로 돌려 `.data/backups/` 의 파일을
다른 곳(클라우드 드라이브 등)에 복사해두세요. Vercel 저장소와 Supabase가 같은 주에
잘못될 경우의 마지막 방어선입니다. 자세한 절차는 `docs/ops-backup.md` 에 있습니다.
